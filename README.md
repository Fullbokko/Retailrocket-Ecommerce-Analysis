# Retailrocket 電商行為分析：與 AI 協作完成的資料分析專案

> **這是我與 AI（Claude）協作完成的資料分析，不是獨立撰寫的傳統分析作品。**
> SQL 語法由 AI 提供；我負責操作分析工具（SQLite、Excel、Tableau）、判斷AI意見與結論是否說得通。分工與限制見〈我怎麼做的〉。
>
> **分析結果：** 4.5 個月的電商行為資料中，91.2% 的成交發生在加購後 1 小時內，所以重點是「讓想買的人順利下單沒有阻礙」。

## 我想回答的問題

> 資源有限，該花在哪裡才有效？哪些是假警報，哪些才是真正該注意的地方？

## 三個主要發現

| # | 發現 | 數字 | 對營運的意思 |
|---|------|------|-------------|
| 1 | **成交很快** | 91.2% 的成交，發生在加購後 1 小時內 | 讓想買的人沒有障礙，自然會下單 |
| 2 | **加購第 2 次是強訊號** | 排除 60 秒內重複點擊後，加購 1 次的成交率 29.4%，加購 2 次 58.9%，3 次 64.4% | 次數越多，代表意願越強，可以優先處理這群人 |
| 3 | **分類之間差異很大** | 加購人數 > 50 的分類中，最高的 814 類別轉換率達 75%（整體轉換率 0.83%） | 值得研究高轉換分類的成功因素，再嘗試複製到其他分類 |

> 這是行為資料的觀察，不是因果。例如「加購第 2 次的人成交率高」，不代表催促就會讓成交率變高，這需要 A/B 測試才能驗證。

## 我怎麼做的：與 AI 協作，以及我的角色

我的背景：理解 SQL 語法，還未能熟練運用，產業知識不夠深入。因此透過「與 AI 協作，完成一個不熟悉領域的完整分析」。

| | 我做的 | AI（Claude）做的 |
|---|---|---|
| 開工前 | 限制AI的Do & Don't、提出目的與需求、他的角色、提供我的環境限制、限制資料取用範圍 | 上網找高手作法以符合我賦與他的角色 |
| 問題與假說 | 決定假說 | 協助討論、補充分析角度 |
| SQL | 執行 SQLite | 撰寫與除錯 SQL，並解釋為什麼這樣寫 |
| 檢查結果 | 用生活經驗判斷AI結論與意見是否符合人性 | 檢查輸出、找出數據上不合理的地方、提出修正做法 |
| 取捨與敘事 | 決定 Dashboard 版面、三個主結論、哪些方向否決 | 提供報告架構與表達建議 |
| KPI 卡片 | 要求 Dashboard 放 KPI 卡，請 AI 給建議（認為這份經過加密、時間跨度短的資料沒有能放的KPI） | 提出三個行為型指標：總瀏覽人數、總成交人數、整體轉換率 |
| Tableau Dashboard | 操作&調整 | 協助解決操作問題 |

**我真正在控管的，是「是否符合人類行為」：**

- **用人的角度模擬一遍。** AI 提出假設或結論時，我會在腦中想：以我遇過、聽過的真實的人，會這樣做嗎？符不符合人性？不符合的就追問、質疑。
- **記錄「已否決的方向」。** 例如因為資料只有 4.5 個月，否決了「加購多次代表長期回購價值」這類推論；一個被推翻的假說也沒有放進主論點。
- **用交接檔管理進度。** 每個階段的狀態、決策、已否決事項、待辦都寫進有版本號的交接檔，讓多次對話能無縫接續，也能回頭追蹤「當時為什麼這樣決定」。

## 驗證被推翻的過程

完整紀錄在 [`docs/analysis_notes.md`](docs/analysis_notes.md)，此處提兩點：

**① 製作 Dashboard 時才想到另一種可能。回頭驗證後，結論翻轉（加購次數 vs 成交率）**

- 「重複加購，會不會只是手滑連點？」
- 改寫SQL後證實**54.6% 的重複加購發生在 1 分鐘內**。符合連續點擊。
- 把 60 秒內的重複點擊排除、重算，曲線由**先升後降**的拋物線變成**持續上升**的水平線。
- 原本以為「加太多次代表猶豫」，需臨門一腳促進購買。修正後確定「加越多次購買意願越高」。

**② 預料外的全推翻（瀏覽集中度）**

- 假說：商品瀏覽次數不低、但訪客很少，只是「觸及不足」，應該加強行銷。
- 第一次查詢得到一整排 0% 轉換率。以為「沒人想買」，反而像是支持這個方向。
- 追查後發現：第一，用來比較的兩個轉換率分母根本不同不能比（瀏覽次數vs加購次數）；第二，每個商品只有約 5~13 位訪客，剛好零成交本來就很常見。
- 對齊單位後，符合條件的商品群轉換率 1.29%，其他商品 0.61%，**沒有任何需求不足的證據**。
- 本以為自己的想法是正確的，也符合人性，但未能證實。

## 限制與誠實揭露

- **資料時間過短，只有 4.5 個月**（2015-05-03 ~ 2015-09-18）：看不出季節性，也不能談長期回購或忠誠度。
- **資料加密處理，假說的空間有限**：資料短、且加密處理過，加上我的產業知識不夠深入，能提出的假說不多，也沒有真實業務經驗可以驗證。
- **金額與訂單量數字是隱碼**：價格欄位是加密的，所以 KPI 改用行為型指標（瀏覽人數、成交人數、轉換率）。
- **21.2% 的商品在屬性表查不到**：因加密關係，「分類」一欄的資料內容無法確認型態，猜測此欄包含字串與數值，但無法拆分進行更廣的分析。
- **分類轉換率的樣本門檻**：SQL 初步過濾 `加購人數 >= 30` ，製作 Dashboard 時又過濾 `加購人數 > 50`。因小樣本 100% 轉換率在這份資料時間跨度會顯得過於誇大（ categoryid 640 只有 33 人）。
- **加購次數 5 次以上樣本很小**（有效加購 1~4 次的配對數為 59,307 / 2,338 / 267 / 73），只能當參考。
- **60 秒的重複點擊門檻**是依資料分布訂的（過半重複加購落在 1 分鐘內），不是業界標準；換成別的門檻，曲線的陡峭程度可能不同。
- **沒有退貨資料**，所以「快速成交」不等於「最後留住的營收」。
- 兩個轉換率單位不能混用：全站 KPI 的 **0.83%** 是「不重複訪客」數；分析瀏覽集中度時用的是「每個商品的瀏覽人數加總」數，數字不同，不能互相比較。

## 如何重現

1. Kaggle 頁面下載 [Retailrocket 資料集](https://www.kaggle.com/datasets/retailrocket/ecommerce-dataset)，匯入 SQLite（說明見 [`data/README.md`](data/README.md)）。
2. 建議先執行索引 `sql/00_setup_indexes.sql`（因資料量大，沒有索引會跑很久）。
3. 依編號執行其他 SQL 檔。
