# 分析過程筆記：假說 → 被推翻 → 修正

這份是整理過的版本，重點放在「原本以為什麼、資料怎麼反駁、後來怎麼修正」。SQL 由 AI 協助撰寫，追查與修正是我與 AI 一起完成的。

## 1. 衝動購物？先猜 98%，實際 91%

- **假說**：加購到成交很快（衝動購物）。
- **第一次**：算平均，得到 2.69 小時。但平均容易被極端值拉走，看不出分布。
- **修正**：改成分區間看分布 → 1 小時內 91.2% / 1-6 小時 4.9% / 6-24 小時 2.0% / 1-3 天 0.9% / 3 天以上 0.9%。
- **學到**：看分布，不要只看平均。
- 📄 `sql/02_impulse_purchase_timing.sql`

## 2. 分類轉換率出現 117.2%

- **第一版**：用「分類總結帳次數 ÷ 分類總加購次數」，結果有分類超過 100%。
- **問題**：轉換率不可能超過 100%。原因是資料裡有人**跳過加購、直接結帳**，分子不是分母的子集，這根本不是漏斗轉換率。
- **修正**：先取「同一人 + 同一商品」的不重複配對，再用 LEFT JOIN，確保成交一定來自加購。
- **學到**：看到不合理的數字（超過 100%、負數），優先懷疑查詢邏輯，不是資料很特別。
- 📄 `sql/03_category_conversion.sql`

## 3. 100% 的類別（640）：新品效應？不是

- **假說**：640 是剛上架的新品，所以轉換率特別高。
- **查證**：它底下的商品最早在 2015-05-14、05-17 就出現，不是新品。
- **結論**：剩下的合理解釋是樣本太小（33 人加購）。所以 Dashboard 只看加購人數 > 50 的分類，第一名變成 814 類別（75%）。
- 📄 `sql/07_category_640_check.sql`

## 4. 加購次數：先升後降 → 持續上升

- **第一版**：原始加購次數，1 → 4 次為 29.9% → 38.5% → 47.6% → 38.8%，看起來先升後降。當時解讀成「加太多次 = 猶豫」。
- **追查**：同一人同一商品的重複加購，54.6% 在 1 分鐘內（10 秒內就佔 42.6%），比較像連點。
- **修正**：60 秒內的重複點擊只算一次，重算有效加購次數 → 29.4% → 58.9% → 64.4% → 65.8%，持續上升。
- **學到**：原本的解讀是被操作雜訊騙了。
- 📄 `sql/04_addtocart_count_vs_purchase.sql`

## 5. 瀏覽集中度：「流量被少數人撐起來 = 觸及不足」？不成立

- **假說**：瀏覽次數不低、但訪客很少的商品，可能是觸及不足，其實有需求。
- **第一次**：結果一整排 0% 轉換率，解讀成「沒人想買」。
- **問題 1**：第一版有「只有 1 個訪客」的極端商品，加了訪客 >= 5 的下限。
- **問題 2**：「瀏覽轉成交率」被拿去跟「加購轉成交率」比，分母不同，不能比。
- **問題 3**：每個商品只有約 5~13 位訪客，以約 1% 的轉換率，剛好零成交的機率本來就高，所以「0%」不是需求不足的證據。
- **對齊分母後**：符合條件的商品群 1.29%，其他商品 0.61%，沒有證據顯示需求不足。
- **結論**：沒有發現異常，也不足以推論更多。這個假說沒有放進 Dashboard 的主論點。
- 📄 `sql/05_view_concentration.sql`

## 6. 兩個轉換率單位

- 全站 KPI **0.83%**：成交的不重複訪客 ÷ 瀏覽的不重複訪客。
- 分析 5 用的 **1.29% / 0.61%**：每個商品的瀏覽人數加總，同一個人看多個商品會重複計入。
- 兩個不能互相比較，Dashboard 只用 0.83%。

## 這個專案裡一直遵守的原則

說出口的結論，必須能回頭找到數據；沒有證據的推測要標示成「延伸思考」，不能跟已驗證的結論混在一起。
